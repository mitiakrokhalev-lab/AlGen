# Масштабирование AlGen: измерения и порядок работы

Обновлено 7 ноября 2026. Цели: полный зафиксированный план за24ч, ×1000 и более
по размеру ручного разбора, завершение всего заявленного плана без OOM.
×100 времени больше не обязательный коэффициент (уточнение Димы); нужны
измеренный суточный бюджет и охват. Это цели, а не достигнутые результаты.
Полнота класса k≤3, s≤2 сохраняется;
оптимизация не разрешает убирать конструкции, свойства или трудные схемы.

Новый этап: C++ числовое ядро и общий minimal. На полном Ulm wall×1,624,
raw-report совпал. На17447922условиях обе бинарные выдачи совпали целиком:
перебор×9,065, minimal×77,840, процесс только этих стадий×5,715;
пик памяти вырос на0,408GiB. Большой report/вердикты не досчитаны.
`metrics-native.json`, `компилируемый-перебор.md`. После CI — сравнительный
stress-codex-02 на прежних8схемах; затем актуальный manifest42баз и оценка
24ч (`суточный-бюджет.md`). На подбор пробной аренды разрешён бюджет
до1000₽/сутки, заказа/оплаты нет. Hirsch остаётся старым открытым флагом
(`пробел-хирша.md`); числовой сорт сам по себе инвариант не реализует.

Ночной этап: stress-01 завершён 5/8, 3 time_budget, 0 missing/наблюдённых OOM;
все восемь измерений и пять полных raw-report независимо проверены.
Первый оптимизированный полный native-контроль: 273,497→261,112 с wall,
перебор 148,502→127,466 с, весь report совпал по SHA. Это одна пара и одна
схема, не ×100 всего класса. Метрики — `metrics-stress01.json`, `metrics-leaf.json`.
Для двух таймаутов следующий bottleneck — повторный minimal по 13–17 млн
условий; возможность пропуска без fixed доказана по коду, ещё не реализована.
Проект точной границы для обновлений — `граница-кандидатов.md`.
Заморожена выборка 24 memory + 6 Putnam; 20 локальных проб, 13 выводов,
6 unknown, нет hirsch. Это частичный аудит: native-проверок выборки 0,
переводы словесных/количественных задач предстоит закончить.

Этап 1 реализован в PR #9 (CI 124 теста OK). На этапе 2 устранён первый
пик загрузчика, RSS 4,54→2,05 GiB при равенстве всех native-битов;
одна прежняя OOM-схема полностью завершилась. Полные данные/ограничения —
`память-codex.md` и `metrics-memory.json`. Бесплатные ресурсы имеют приоритет,
варианты исследованы в `ресурсы-вычислений.md`; аренды и оплаты не создавались.

Следующий шаг этапа 2: Search solver стал отложенным, на том же полном native
контроле пик процесса 6,00→5,17 GiB (−0,821 GiB); весь report побитово совпал,

## Три показателя успеха

Время считаем отдельно: холодная сборка таблиц; полный первый перебор;
повторный перебор с кэшем; быстрое обновление примера; окончательное
восстановление минимальности и базиса после обновления. Записываем wall,
CPU дерева процессов, цену всех ошибок/повторов и стоимость диска.
Заявленный коэффициент проверяется на одинаковом полностью завершённом наборе и ресурсах.
Пилот с 50 проваленными/отсутствующими схемами таким эталоном ещё не является.

Для выдачи нужны два знаменателя: `Qraw/Qbasis` и `Qkept_old/Qbasis`.
На нынешнем успешном подмножестве ×1000 от 1 247 289 неизвестных № означает ≤1 247
вопросов, ×10000 — ≤124. ×1000 от уже сжатых 7 872 означает ≤7 вопросов;
это другая, гораздо более сильная цель. Все свёрнутые формулы остаются в
архиве с проверенными источниками. Компактная печать сама по себе не решает
математических вопросов. Универсальная задача-схема считается одной единицей
ручной работы только при проверяемом охвате её экземпляров.

Память: 0 OOM, 0 молча потерянных схем; запланировано=успех+явные незавершения.
Измеряем пик каждого процесса и всего дерева/cgroup, RSS по этапам, размер
живых условий, кэшей, report, число SAT-переменных/клауз, объём диска.
Целевой рабочий бюджет — не более 80% фактического лимита машины/cgroup
(порог предварительный). Если задача не помещается, делим работу или
выгружаем блоки на диск; не отбрасываем математические условия.

## Последовательность изменений

| Этап | Конкретное изменение | Что измерить и проверить перед переходом |
|---|---|---|
| 0. Учёт | Единая JSON-статистика, фиксированный список схем, контроль охвата | Ошибки и отсутствующие не исчезают; пересчитаны 42 базы и план класса |
| 1. Надёжное обновление | Исполнитель очереди, замороженные входы, полный перебор, проверка всего базиса, атомарная публикация | Сбой/новый пример/новая схема не закрывают старый долг; появились новые минимальные надусловия |
| 2. Память | Профиль тяжёлой схемы; затем блоки числового report, интернирование атомов, потоковый вывод/SQLite, ограниченный банк/кэши | Побитовое сравнение выдачи; все схемы малого стресс-набора завершаются с измеренным пиком |
| 3. Выдача | Межсхемный базис, учёт всех свёрток; ранжирование пробелов по влиянию; точечные GAP/доказанные значения | Каждый удалённый из ручной выдачи вопрос имеет доказанную свёртку, теорему или конкретный контрпример |
| 4. Время | Профиль на полном стресс-наборе: кэш доказанных вердиктов, общие подзадачи схем, скомпилированный числовой цикл | Полный отчёт совпадает, выигрыш отдельно cold/warm; изменившиеся ядра/источники явно отмечены |
| 5. Общие шаблоны | Канонические вопросы с подстановками, областью применимости и графом зависимостей | Проверен каждый экземпляр, опровержение раскрывает всех зависимых; шаблон не объявлен теоремой |
| 6. Большая теория | Точное локальное/ленивое заземление с проверкой пропущенных правил | Эквивалентность полному заземлению; SAT частичной теории не принимается за SAT полной |
| 7. Масштаб | Пилот нескольких разных баз, затем весь зафиксированный класс | Измеренный бюджет, 100% схем, матрица покрытия 541 карточки, все три цели оценены вместе |

Приоритеты 2–4 уточняются профилем; новые математические данные способны
одновременно уменьшить живые условия, время SAT и остаток. Первые кандидаты:
Aut/Inn/Out/Φ/факторы синтетических произведений; решающие неизвестные
значения; правило finite(G)⇒finite(Sym(G)) и диагностика ослабленного
заземления. 3 289 текущих вопросов содержат primitive(regular-act(G));
это частота атома, а не обещание закрыть их одним правилом.

   Следующие кандидаты по профилю — report, кэши и банк моделей.
   После исправления повторять именно контрольный набор, без обещания множителя до замера.
4. После устранения OOM измерить полный глобальный базис и целевые пробелы;
   сделать один пакет проверенных данных/правил и сравнить все показатели.

Ближайшие идеи времени: одинаковые строки таблицы объединять с весами, если
сохраняются все пороги, индексы и порядок; затем переносить горячий числовой
цикл из Python в скомпилированный код. Более сильная исследовательская идея —
искать следующий вопрос, не следующий из текущего базиса, с отдельной полной
проверкой покрытия пропущенных кандидатов. Пока это идеи, не реализованные
ускорения. Измерять сначала профиль, затем совпадение полного результата.

Ближайшие идеи выдачи: единый базис между схемами и общие задачи с
проверенными подстановками; ранжировать недостающие значения библиотеки по
числу зависимых вопросов. Меньше печатать и решить меньше математических
вопросов — разные результаты, они считаются отдельно. Общая схема не
становится доказанной теоремой до ручного доказательства или вывода библиотекой.

После заметного шага обновляются `status.md`, этот план и JSON соответствующего
замера; указываются версия кода, входы, режим, ресурсы, проверки и нерешённые
проблемы. Копии `claude/status.md` в репозитории нет; внешний Claude-документ
из этой среды недоступен. Эти копии нельзя выдавать за обновлённые.
