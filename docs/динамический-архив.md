# Динамическая библиотека строк и архив

Первый рабочий контур, 6.11.2026. Код — `py/algen/live.py`, подключение к
перебору — `live_bridge.py`. Используется стандартная SQLite, дополнительных
зависимостей нет. Обычный прогон без новых флагов работает прежним путём.

## Что обновляется сразу

Архив хранит исходные строки выдачи, вопросы, доказанные факты, варианты
симметрий, зависимости сжатия и конкретные подстановки с известными
значениями. Индекс «атом → варианты вопросов» ищет опровержения новой строкой.
Все литералы одного варианта, включая гипотезы класса, должны быть известны
и верны в ОДНОЙ подстановке. Отсутствие значения не считается ложью. Источники
разных строк не объединяются в контрпример.

При опровержении вопроса зависимые строки раскрываются транзитивно. При
исправлении значения или отзыве примера вопрос возвращается, если других
контрпримеров нет. Старые версии, источники и исходные вердикты не удаляются.
Связи могут быть внутри схемы или иметь вид `SID:№` между схемами. Коллизии
локальных номеров и циклы вызывают откат импорта. Неразрешённая ссылка, в том
числе «экземпляр: …», оставляет вопрос открытым и ставит долг пересжатия.

Исходные строки с вердиктами «короткий довод», «трудный контрпример», ошибки и
противоречия тоже сохраняются в records. Они доступны отдельно от очереди
вопросов. Факты без посылок экспортируются из сводки вместе с полным report.

## Граница полноты

Быстрое обновление не создаёт новых минимальных условий. Например, старый
минимальный вопрос `p ⇒ q` опровергнут новой строкой, но `p ∧ r ⇒ q` впервые
становится минимальным. Поэтому при изменении библиотеки ставятся два задания:
`enumerate` (полный перебор с прежним SAT-кэшем) и `compress` (новый базис).
Они объединяются по контексту и ревизии, а не размножаются на каждое значение.

Очередь сейчас является явным долгом: фонового worker и автоматического
снятия заданий нет. Новый полный прогон, импорт его снимка и пересжатие —
следующие операции контура. Пока они не выполнены, число открытых вопросов
не выдаётся за окончательный базис всего класса.

Контекст включает базу, класс, теорию, исходную библиотеку, объявление,
переменные и fixed. Данные разных теорий/классов не смешиваются. Новый снимок
библиотеки получает отдельный контекст. Активные дополнительные строки можно
перенести командой carry при неизменной теории и области; история остаётся.
Перенос при изменении теории отклоняется до перепроверки данных.

## Как получать архив

Команды из каталога `py/`. Для выбранных схем существующей таблицы:

```sh
ALGEN_SIZE=2 ALGEN_FAST=1 ALGEN_STATE_SAVE=1 ALGEN_DYNAMIC_EXPORT=1 \
python3 -B -m algen.table перебор G --посылок 3 --нитей 1 \
  --каталог ../tab --выход ../run --схемы SID

python3 -B -m algen.live ../archive.sqlite import ../run/SID.archive.jsonl.gz
python3 -B -m algen.live ../archive.sqlite status
```

`SID` заменяется настоящим идентификатором схемы. Первый запуск пишет
`SID.archive.jsonl.gz` атомарно и потоково. В нём ВСЕ строки report, включая
свёрнутые, и безусловные факты. Включение флага поверх готового каталога не
пропустит схему без подходящего экспорта: проверяются заголовок и отпечаток.

Первые stdout-строки import/status дают context — его передают следующим
командам. Повторный импорт одной и той же схемы отвергается, чтобы не затереть
снимок. Для следующего прогона используется новый каталог/снимок; схема с
новыми данными не подменяет старую историю молча.

Старые summary с одними «оставленными вопросами» не восстанавливают скрытые
формулы. Их можно импортировать через API как частичный снимок (complete не
ставить), но это явно неполный архив. Полнота отмечается отдельно у каждой
импортированной схемы и не означает покрытие всех схем класса.

## Добавление данных

Пакет — конкретная подстановка, известные значения атомов и источник:

```json
{
  "key": "V4-example",
  "assignment": {"G": ["obj", "4:2"]},
  "facts": {"abelian(G)": true, "cyclic(G)": false},
  "source": {"kind": "library", "reference": "data/finite/grp-small.jsonl: 4:2"}
}
```

Это пример формата. В рабочем цикле пакет получается через
`live.library_row(form, row_index, reference)` из настоящей подстановки
Library и её рассчитанной матрицы. Неизвестные значения в пакет не попадают.
Метаданные source записывают происхождение уже проверенных данных; они не
заменяют математическое доказательство или проверку GAP. Новые математические
значения по-прежнему требуют обоснования и независимого проверяющего.
SAT-модель как источник примера группы отклоняется.

```sh
python3 -B -m algen.live ../archive.sqlite add-example CONTEXT packet.json
python3 -B -m algen.live ../archive.sqlite export CONTEXT --state refuted
python3 -B -m algen.live ../archive.sqlite export CONTEXT --state open
python3 -B -m algen.live ../archive.sqlite records CONTEXT SID
```

Дополнение фактов объединяется только с той же assignment. `null` явно
отзывает значение; `0/1` вместо JSON bool отклоняются. Для исправления bool
нужен `--replace`: пакет заменяет прежний набор значений целиком. Отзыв всей
строки — `withdraw CONTEXT KEY source.json`. История сохраняется; свидетельство
содержит точный сработавший вариант запрета и цепочку источников.

Если новая строка опровергает доказанный теорией факт, вся транзакция
откатывается: это ошибка данных или теории, а не повод переписать вердикт.

## Полный перебор с динамическими строками

```sh
ALGEN_SIZE=2 ALGEN_FAST=1 ALGEN_STATE_SAVE=1 ALGEN_DYNAMIC_EXPORT=1 \
ALGEN_DYNAMIC_DB=../archive.sqlite ALGEN_DYNAMIC_CONTEXT=CONTEXT \
python3 -B -m algen.table перебор G --посылок 3 --нитей 1 \
  --каталог ../tab --выход ../run-next --схемы SID
```

Мост добавляет активные строки к матрице ВИДА схемы, проверяет совместность с
теорией и вызывает обычный `_derive`. Поэтому новый полный перебор реально
видит добавленные значения и может найти новые минимальные условия. SAT-кэш
остаётся пригоден при той же теории. Отпечаток результата включает контекст,
ревизию, содержимое активных примеров и код моста — разные SQLite-файлы с
одинаковым числом обновлений не используют чужие результаты. Если библиотека
изменилась между планированием и началом схемы, требуется перепланирование.

Старая G-таблица generic_filter может не знать новых примеров. Поэтому в
динамическом режиме этот отбор не применяется; безопасно остаются лишние
вопросы. instances использует обновлённую матрицу самой схемы. Режим пока
требует CLOSE_MARKED=True, как в текущем рабочем конвейере проекта.

Слой SQLite дополняет базовую таблицу. Исправление/отзыв его строки не удаляет
native-строку исходной Library: ошибку в исходных данных исправляют там и
перестраивают таблицы. Образы новых объектов не выдумываются: дополнительные
строки знают только переданные и выведенные значения, а неизвестный образ
остаётся неизвестным. Автоматический поиск GAP и материализация новых моделей
в исходную Library — следующий шаг, не выполненная часть этого изменения.

После импорта полного нового снимка:

```sh
python3 -B -m algen.live ../archive.sqlite carry OLD_CONTEXT NEW_CONTEXT
```

Так дополнительные примеры не теряются при смене библиотечного снимка.
Очередь в новом снимке остаётся консервативной; доказательства полноты нового
базиса автоматическим переносом не подменяются.

## Проверки

- 18 узких тестов: неизвестное/ложное, раздельные подстановки, fixed, варианты
  симметрий, разные контексты, история, откат конфликтов, межсхемные циклы,
  раскрытие зависимостей, content fingerprint и новое минимальное надусловие.
- На случайных таблицах 60 последовательных обновлений сверены с полным
  перебором всех известных строк при каждом обновлении.
- Проверяющий нашёл и помог исправить потерю manual-строк, уже опровергнутого
  родителя, коллизию отпечатков разных SQLite и скрытый долг пересжатия.
- Контрольная реальная схема G, Z(G), исходная библиотека теста только C1:
  добавление C2 сняло 840 старых вопросов из 3 233; доказанные факты сохранены.
  Быстрая стадия — 0,0369 с, повторный полный E.run — 7,1002 с. Матрица и
  логические вердикты совпали со свежим прогоном на C1 и C2. Это малая проверка
  механизма, а не оценка ускорения полного проекта; полный перебор остаётся
  необходимым, его стоимость не исчезает.
- Частичная копия настоящего остатка пилота 16б: сохранены все 7 872 видимых
  вопроса из 43 схем с непустым остатком, импорт — 2,302 с. Добавление проекций
  семи уже известных групп (1, C2, C3, V4, S3, Z, F2) заняло по 0,024–0,030 с
  и не сняло вопросов. Сам индекс не заменяет новые математические данные;
  следующий шаг — целевые пробелы и поиск новых контрпримеров. У этого
  старого summary нет скрытых формул, поэтому импорт отмечен частичным.

## Исполнитель очереди

`live_worker` фиксирует полный список **импортированных** схем и их точные
параметры генерации. Это не весь класс проекта. Старые экспорты без
`generation` нужно пересоздать; частичный summary не подходит. Первая версия
поддерживает SIZE>0, CLOSE_MARKED=True, без skip/defer; она явно отклоняет
другие режимы. Работает один исполнитель на SQLite-файл.

```sh
cd py
python3 -B -m algen.live_worker ../archive.sqlite plan CONTEXT \
  --tables ../tab --out ../worker-run-001
# Команда печатает id плана.
python3 -B -m algen.live_worker ../archive.sqlite run RUN_ID \
  --state ../previous-run --limit 3600 --memory 2
```

План сохраняет ревизию, хэши активных строк, всей области схем, кода, данных,
native-таблиц и кэшей представителей. Небольшой `input.sqlite` содержит только
активные строки, без копирования всего raw-архива. Производитель видит
замороженные входы; новые примеры разрешено добавлять параллельно, но такой
прогон уже не сможет снять долг изменившегося снимка.

Полный перебор выполняется штатным table с одной нитью, затем новый архив
собирается на диске. В глобальное сжатие идут **все** неизвестные nonrefuted,
включая прежние свёртки и раскрытые внешние экземпляры. Проверяются все
зависимости базиса и совместность фона, а не выборка из 1000. Обычная CLI
compress_base сохраняет прежнюю выборочную проверку; worker всегда требует
`--полная-проверка`. Исходные формулы и ручные категории остаются в records.
Новый базис может иметь другие источники и порядок, чем прежнее сжатие;
побитовое совпадение графа сжатия не заявляется.

Нулевой exit code недостаточен: worker проверяет все ожидаемые схемы,
параметры/контекст/nonce, статусы, ошибки вердиктов и сжатия, отсутствие
противоречащих строк, CRC gzip, число raw-записей и классы сводки. Неполный,
устаревший или непроверенный результат очередь не очищает. Перед возобновлением
повреждённые JSON/экспорты перемещаются в `rejected/`, чтобы table пересчитал
их; существующие файлы не удаляются. Новый staging при повторе также сохраняет
прежний. Рабочий кэш Library изолирован: прежние кэши проекта не очищаются.

После повторной проверки входов одним SQLite commit публикуются все схемы,
происхождение примеров, новый граф, successor и квитанция, закрывается долг.
Старый контекст сохраняется, его `status` указывает successor; новые примеры
нужно писать в этот новый контекст. Попытка изменить завершённый снимок
отклоняется с его адресом. Повтор completed возвращает сохранённую квитанцию.
Она хранится в `worker_runs.detail`; `receipt.json` — дополнительная копия,
ошибка её записи не отменяет успешный commit. Артефакты и логи — в каталоге
плана; `status` показывает план/ошибку/завершение.

`--memory` — существующий дополнительный RLIMIT_AS дочерней схемы, не лимит
RSS всего worker/сжатия. Большие архивы и глобальный SAT-базис ещё требуют
профиля и ограниченного хранения; отсутствие OOM на всём классе пока не
достигнуто. Масштабный повтор пилота — после измеренных улучшений на малом
контрольном наборе. Следующие направления и точные критерии —
`план-масштабирования.md`.

Малый контроль с настоящими правилами и группами C1/C2 (ограничены Library,
native-таблица и список схем; кэш вердиктов отключён, CLI вызывается внутри
процесса; теория и SAT настоящие):

```sh
cd py
python3 -B -m tools.check_live_worker --out ../work/control-worker-001
```

Он проверяет путь CLI→перебор→архив→базис→публикация и сохраняет
`result.json`/`control.log`. Это контроль механизма, не бенчмарк всего класса.
Подпроцессы и файловый кэш проверяются отдельно, этот helper их не покрывает.
