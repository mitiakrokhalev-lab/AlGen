Каждая схема идёт отдельным процессом на стандартном публичном GitHub runner
Ubuntu 24.04, максимум четыре runner одновременно. Лимиты процесса: 1 200 с
wall и 12 GiB RSS; опрос 0,25 с может допустить превышение между измерениями.
Job ограничен 30 минутами вместе с установкой и скачиванием, сводка — 20.
Восемь бюджетов процесса дают максимум 9 600 с в сумме, две волны при четырёх
runner — 40 минут. Вместе с очередью, загрузкой и сводкой ориентир 45–60 минут;
при задержках GitHub может быть дольше. В этой сессии ничего не оплачивается.

Library, каркас и native-таблицы переиспользуются из run `42173383257`.
До выполнения проверяются текущий fingerprint и SHA256 всех 23 входных
файлов. Отсутствие/повреждение кэша останавливает case до возможной пересборки.
Артефакты исходного run ограничены сроком хранения: если недоступны, это
явное незавершение, а не повод незаметно строить другую библиотеку.

Каждый case сохраняет measurement, этапы, summary и весь raw report в gzip;
артефакты пилота хранятся 30 дней. Сводка перечисляет все восемь ID, включая
ошибки, остановки и отсутствующие. Статус ok требует штатного завершения,
совпадения библиотеки/термов/параметров, нуля противоречащих строк, проверки
CRC, SHA и числа строк полного report и точного kept/folded/источников.
Для Ulm задан известный SHA прежнего полного native-контроля. Два теста
проверяют также повреждённые gzip, поддельную свёртку, неверные лимиты,
превышение бюджета и сохранение остальных case при ошибке одного.

Время wall и CPU учитывается также у неуспешных процессов, где записано;
отсутствующее время не равно нулю. Сумма wall процессов отличается от wall
workflow. RSS означает пик одного процесса, не дерева/cgroup. Отдельный
процесс на case пока не проверяет накопление памяти между несколькими схемами.
Выдача и коэффициент сжатия считаются только для проверенных ok, с явным
знаменателем по unknown-ID, отдельно от первых вердиктов классов.

Baseline 16б использовал тёплый кэш вердиктов, а поле времени схемы исключало
startup. Новый профиль этот кэш не загружает и считает wall с startup.
Прямой коэффициент ускорения по этой паре считать нельзя. Для честного
сравнения времени позже нужны совпадающие режимы/входы и законченный набор.
Проверки сводки подтверждают целостность и согласованность полного отчёта;
нового SAT-доказательства всего межсхемного базиса этот workflow не выполняет.

После завершения: скачать артефакты, независимо проверить сводку, записать
в status.md/JSON полный охват, время, память, выдачу и цену ошибок; по этапам
выбрать следующую оптимизацию. Затем — несколько других баз и, после
подтверждённого бюджета, более широкий пилот.
