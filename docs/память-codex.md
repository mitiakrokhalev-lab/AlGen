# Первое устранение пика памяти

6 ноября 2026, `codex/bounded-memory`, поверх PR #9. Полный класс и фильтры
не менялись. Существующие таблицы читаются с прежним отпечатком, без STALE.
Все замеры ниже локальные, новых больших GitHub-пилотов не запускалось.

## Найденная причина и исправление

Сначала загрузчик читал упакованные по строкам native-части, распаковывал
**всю** матрицу в плотный bool-массив, затем паковал её по столбцам. Для
G (30 753 строки × 89 298 литералов) одна временная плотная матрица занимает
около 2,56 GiB, сверх уже загруженного каркаса, решателей и packed-частей.
Малые замеры RSS только в начале/конце схемы этот пик не показывали.

Новый `PackedCols.from_packed_rows` распаковывает и перепаковывает блоки,
собирая их через границы частей. Блоки кратны восьми строкам, хвост и padding
добавляются один раз в конце всей таблицы. По умолчанию целевой размер
плотного блока — 64 MiB (не менее восьми строк). Конечное представление,
порядок строк, число столбцов и padding совпадают со старым. Контрольный
прежний путь — `ALGEN_STREAM_TABLE=0`.

Второе изменение: если в `E.run` список проверяемых вырождений `degen` пуст,
не строится кэш `frozenset(whole)→False`. Ответ прежде всегда был False,
SAT-вызовов не было. При непустом degen прежний путь сохранён, в том числе
для скрытых переменных графа. Для сравнения старое поведение включается
`ALGEN_DEGEN_EMPTY_CACHE=1`. Большой отдельный выигрыш этого изменения пока
не измерен — не прибавлять его к результату загрузчика без нового замера.

текущими библиотекой/теорией. Машинные результаты: `metrics-memory.json`.

## Настоящая тяжёлая схема

У среды фактический cgroup-лимит 8 GiB; сведения MemTotal хоста больше и не
являются доступным бюджетом. Профиль запускает одну схему, опрашивает RSS
каждые 0,25 с и останавливает дочерний процесс по порогу 6,4 GiB либо времени.
Это порог наблюдения, не жёсткий лимит: между опросами возможно превышение.
`peak_rss_kib` — максимум процесса по Linux rusage, не пик дерева/cgroup.

На `G-12-13-705-707-708-709` (rank/profinite, k=3) прежний загрузчик достиг
≈6,68 GiB уже при чтении таблицы и был остановлен. После исправления загрузка
прошла с наблюдённым пиком ≈4,84 GiB, затем начался настоящий перебор.
В 180 с весь процесс был остановлен по времени с пиком ≈4,92 GiB.
**Завершение схемы и устранение всех её OOM не заявляются.** Оба незавершённых
замера и дополнительный разбор стадий загрузки включены в JSON.

Разбор выделил также две копии SAT-решателя каркаса (каждая добавила около
0,82 GiB), а затем работу перечислителя условий. Эти потребители не устранены
данной правкой. Дальше профиль report, кэшей SAT, банка моделей и сжатия;
ограниченное хранение/выгрузка на диск, без потери условий.

Дополнительно полностью завершена настоящая схема
`G-15-320-705-707-708-709`: G, Ulm(G), Ulm(Ulm(G)), k=3. В пилоте 16б она
падала с MemoryError. Теперь полный процесс с загрузкой занял 282,466 с,
сама схема — 197,8 с, CPU процесса — 282,323 с; пик RSS — 6 286 356 KiB,
то есть ≈6,00 GiB. Матрица native целиком, 30 753 строки; противоречащих
строк — 0. Report содержит 3 671 строку, SHA256 сохранён в JSON. В сводке
1 781 неизвестный, 90 выводимых и 7 опровергнутых классов; оставлено 9 вопросов.
Это один контрольный успешный случай, не повтор всего пилота. Сравнивать
его время со старым оборвавшимся запуском как ускорение нельзя. Исторические
55/105 успехов пилота не переписываются задним числом.

Учтена цена **всех шести** локальных профилирующих процессов, включая
остановленные: сумма wall 579,340 с, CPU 578,515 с. Тесты в эту сумму не входят.

## Повторение

Нужны исходные `tabs` и `skel` указанного запуска, распакованные в отдельные
каталоги. Кэш Library берётся из архива skel, ничего не пересоздаётся.

```sh
cd py
python3 -B -m tools.profile_memory \
  --tables ПУТЬ/таблицы --skel ПУТЬ/skel --library-cache ПУТЬ/кэш \
  --scheme G-12-13-705-707-708-709 --out НОВЫЙ_КАТАЛОГ \
  --seconds 180 --rss-gib 6.4
```

Для отдельного контроля storage добавить `--table-only`, а для старого пути
также `--legacy-table-load`. Результаты: `measurement.json`, `stages.jsonl`,
`rss.jsonl`, `process.log`, а при завершении схемы — её настоящие JSON/TXT и
кэш вердиктов. Код и параметры фиксируются в измерении. `complete=false`
при остановке, ошибке или отсутствии успешного результата схемы.

Тесты `test_memory.py` проверяют биты на границах частей/блоков, пустые и
некратные восьми размеры, ограниченность распаковки, три матрицы и метаданные
настоящего загрузчика, точное равенство report/порядка/ядер при обоих режимах
проверки вырожденности, а также нормализацию путей и аварийное завершение
профилирующего процесса. Полный локальный набор и независимые проверки
записываются в status.md после завершения.
