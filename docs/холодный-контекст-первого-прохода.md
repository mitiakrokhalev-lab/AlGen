# Общий контекст для первого прохода очереди знаний

15.11.2026. Кандидат оптимизации, **не реализован и не измерен парным опытом**.
Он относится к экспериментальному слою значений; основной E.run остаётся
прежним. Пройденный контроль не следует запускать снова без этой новой причины.

## Что установлено

В проверенном контроле 43684395730 Theory содержит 3264381 атом и 34305956
клауз. Подготовка снимка вместе с первым поиском занимает 55,191877462 с,
повторное открытие с новым контекстом и восстановлением — 55,972014057 с.
Эти таймеры включают несколько действий: они не выделяют стоимость одного
хэширования, одного Solver bootstrap или одного SAT-запроса.

В table.view свежий SchemeForm получает `v.sc = b.sc`, а его атомы и столбцы
выбираются из базовой формы. Следовательно, разные виды одной базы могут
разделять тот же `sc.T`. Текущий FrozenRowTheory для каждого нового объекта
снова обходит полную схему, хэширует клаузы и создаёт собственный Solver при
первом запросе. Контроль намеренно повторяет эту работу для проверки reopen.

## Следующая реализация

Разделить неизменяемую основу Theory и небольшой контекст вида. Основа хранит
точную полную схему, закреплённые буферы клауз, версии и приватный решатель.
Контекст вида хранит полный типизированный список его атомов, отображение
литералов и собственную идентичность; журнал условий каждого вида остаётся
отдельным. Разные базы, разные Theory или разные области не склеиваются.

Для одного последовательного worker основу можно подготавливать один раз
на неизменяемое поколение базы, затем обслуживать несколько **разных** схем
первого прохода. Это возможное повторное использование внутри первого расчёта,
а не результат тёплого запуска всей уже рассчитанной схемы.

Смена вида не добавляет в Solver постоянных фактов строки, fixed или hints:
прямые факты передаются только assumptions. Иначе последующий вид получил бы
чужие предпосылки. Learned clauses допустимы лишь как следствия неизменной
основы. Доступ последовательный, изменение mutable Solver снаружи запрещено.
Все прежние проверки совместности источников, core и противоположного значения,
транзакционных границ и отзыва опор сохраняются.

Нужен явный контроль жизненного цикла. Если поздний участок E.run добавил
атом/клаузу либо сменились буферы или содержимое, прежняя основа непригодна.
Нельзя незаметно перенести её Solver или доказательства на новую версию.
Необслуживаемый вид оставляет явный долг; это не разрешение сузить класс.
Перед подключением следует проверить, можно ли подготовить полную схему
допустимых атомов заранее для всех видов соответствующей базы.

Отдельный кандидат — пакет нескольких выводов одной строки: одна проверка
всех прямых источников, отдельное обоснование каждого вывода и одна атомарная
публикация полной проекции/реклассификации. В текущем API каждый derive создаёт
событие и новую ревизию; будущий пакет требует собственного контракта retry и
проверки сбоя. Пропуск проверки отдельного значения или долга условий недопустим.

## Проверка до вывода об ускорении

Сначала выделить таймеры схемы/клаузного хэша, Solver bootstrap, совместности,
вывода, source/proof-транзакции и реклассификации. Не приписывать целиком 55 с
одному действию и не умножать этот таймер на число схем для бюджета класса.

Парный опыт: два разных полных сохранённых домена одной базы, одинаковые
входы/порядок/источники/ограничения, отдельный свежий процесс на каждый режим.
Первый режим создаёт отдельную основу на вид, второй переиспользует общую
основу между двумя видами. Холодная подготовка и первый вид входят в оба
полных таймера. Один и тот же заранее рассчитанный вид дважды не заменяет опыт.

Сверить все внешние проекции, сохранённые коды, исходные поддержки и порядок,
proof/core/версии и отзывы, а также смешение противоположных предпосылок двух
строк. Потребуются случаи alias, fixed, пар и позднего изменения Theory.
Полный report E.run сравнивается только при одинаковом домене/полном покрытии;
классификация сохранённых кодов сама по себе не является этим report.

Измерять wall/CPU/RSS и число подготовок/решателей, включая ошибки и память
долгоживущей основы. Полную схему с неизвестными условиями выбирать после
проверки бюджета хранилища. Прототип одной малой схемы не подтверждает бюджет
остальных 41 базы, суток или размера ручной очереди. Полная граница кандидатов,
актуальные поддержки, надёжная очередь и математические источники остаются
самостоятельными блокерами; все девять gates полного запуска открыты.
