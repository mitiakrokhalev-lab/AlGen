# Отложенное создание SAT-решателя Search

7 ноября 2026. Ветка `codex/deferred-search` поверх PR #10.

Профиль обнаружил две постоянные копии решателя одного каркаса: `sc.s`
обслуживает форму, а `Search.s` нужен для `entails`/`witnesses`. При чтении
готовой таблицы Search используется для образов, фактов, имён и подстановок;
эти операции его SAT не запрашивают. Неиспользуемый второй экземпляр занимал
около 0,82 GiB в native-каркасе G.

## Реализация и совместимость

`deferred.make_search` переиспользует настоящий конструктор Search и передаёт
ему адаптер фабрики solver. После конструктора `search.T` восстанавливается
как исходная Theory. Поля/выбор объектов/порядок подстановок задаёт прежний
Search. Все options передаются в исходный конструктор. Существующая подмена
`E.Search` также получает исходную Theory и работает прежним способом.

`DeferredSolver` создаёт отдельный экземпляр при первой операции SAT;
основной `sc.s` не заимствуется. `delete()` до открытия не вызывает фабрику,
повторное удаление безопасно, после удаления запрос явно отклоняется.
Служебные обращения pickle/deepcopy не открывают SAT; solver-handle не
сериализуется. Формат skeleton-кэша прежний: search/solver исключаются из
снимка. Изменены оба пути создания табличной формы — новый SchemeForm и
чтение сохранённого skeleton. Прямые вызовы Search сохраняют своё поведение.

`ALGEN_EAGER_SEARCH=1` возвращает немедленное создание поискового solver.
Профайлер поддерживает этот режим через `--eager-search`, потому что сам
задаёт явное окружение. Класс задач, теория и матрицы не менялись.
library.py/logic.py не менялись: native-fingerprint
`73a2a35d2480ac9c:G::s2:быстро` сохранён, таблицы и библиотеку не перестраивали.

## Проверки и повторение

Тесты `test_deferred.py`: фабрика вызывается один раз; SAT/ядра/модели и
добавление клауз работают; удаление и служебные probes не создают solver;
ошибка фабрики не оставляет частичный объект; все факты/матрицы/подстановки,
report/ядра/порядок совпадают; реальный контрпример находится после удаления
основного solver; старый кэш читается, новый сохраняется без solver/search.

Первый полный набор выявил регрессию подменного `E.Search` в тесте полноты.
Она исправлена, отдельная проверка добавлена; повторный полный набор и
независимые проверки фиксируются в status.md. Никакие тесты не отключались.

```sh
cd py
python3 -B -m tools.profile_memory \
  --tables ПУТЬ/таблицы --skel ПУТЬ/skel --library-cache ПУТЬ/кэш \
  --scheme G-15-320-705-707-708-709 --out НОВЫЙ_КАТАЛОГ \
  --seconds 330 --rss-gib 6.4 --save-report
```

Для прежнего режима добавить `--eager-search`. `--load-only` ограничивает
контроль загрузкой настоящего каркаса/таблицы, без перебора. `--save-report`
пишет raw report по одной строке в gzip для аудита; это не live-export с
контекстным заголовком. Остановка/ошибка по-прежнему даёт `complete=false`.
Большой пилот не запускался. Дальше — report, кэши и банк моделей, затем
контроль других трудных схем и нескольких баз. Цели ×100/×1000 и отсутствие
OOM на всём классе ещё не достигнуты.
